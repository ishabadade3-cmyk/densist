# Data model baseline

Types below are PostgreSQL types. `NOT NULL`/`NULL` are explicit. `id` values are UUIDs generated with a cryptographically secure random generator and exposed as opaque public identifiers; sequential IDs are never exposed. This task implements the documented schema. Sensitivity: public / personal / clinical.
Every table includes `created_at timestamptz NOT NULL` and `updated_at timestamptz NOT NULL`, including tables whose original entity-column list omitted them. The migration initializes both timestamps on insert and maintains `updated_at` on updates with the database clock. This additive timestamp decision follows explicit task direction.
Auth role values used by the API are `patient`, `dentist`, `receptionist`, `clinic_admin`, and `system_admin`; anonymous visitor access is not a stored role. Session tokens are random opaque values in secure cookies; only SHA-256 token digests are stored in `auth_sessions`. MFA ciphertext is encrypted with an external key; rate-limit subjects are keyed hashes, not raw identifiers.

**Scheduling invariant (FR-013):** PostgreSQL `btree_gist` exclusion constraint on active appointment rows, independently for dentist and operatory: `EXCLUDE USING gist (dentist_id WITH =, tstzrange(start_time,end_time,'[)') WITH &&)` and equivalent `(operatory_id WITH =, tstzrange(...) WITH &&)`; exclude cancelled/rescheduled legacy rows. T-008 API values are `requested`, `confirmed`, `cancelled`, `completed`, and `no-show`; transition graph and null-operatory policy remain TBD:appointment_transition_policy / TBD:operatory_policy. Enforce in a transaction; application checks alone are insufficient.

The source analysis also proposes `patient_clinical_alerts` and `otp_verifications`; schedule/leave, invoice, waitlist, family link, stage, and operatory additions are in analysis §4.1. `patient_family_links` is the analysis name; research suggests guardianship verification. Additional role-specific schedules, document-release metadata, consent evidence, billing tax calculations, and cascade behavior require confirmation.

Notifications use a database queue with separate channel and purpose fields. A send requires the latest explicitly recorded consent for the exact patient, channel, and purpose immediately before each provider call; legacy channel-less consent never authorizes a send. Marketing is a distinct purpose from clinical-care and transactional notices. SMS templates require an approved DLT template ID and sender ID, typed/bounded variables, fixed intervening text, and no URL until a DLT-whitelist policy is confirmed. `notification_attempts` stores provider IDs and status/error codes only; rendered message content is not copied into logs. Old notification rows with no template/idempotency context are preserved but excluded from dispatch. Provider adapters and all retention, reminder, and retry policies remain TBD.

Clinical records additions: `medical_record_versions` stores immutable snapshots written alongside each note create/edit; `patient_medical_histories` stores dentist-entered entries; `clinical_documents` stores metadata only while bytes are held under a private storage root. Public IDs are UUIDv4 generated server-side. Documents currently accept PDF only, are capped by `CLINICAL_MAX_UPLOAD_BYTES`, and have authenticated signed links expiring per `CLINICAL_SIGNED_URL_TTL_SECONDS`; the configured values/provider scan/storage-at-rest controls remain subject to OQ-038–OQ-040. The validator rejects malformed PDFs and selected active-content markers but does not provide malware scanning.

Payment records keep provider order and payment IDs, an idempotency key, method, refund totals and opaque receipt number. New payment transitions are pending→successful/failed, failed→successful only on a verified captured payment, successful→partially_refunded/refunded, and partially_refunded→refunded; late failure/capture events cannot reverse a refund. `offline_method` stores only one of the API's fixed method codes (`cash`, `bank_transfer`, `upi`, `other`); free-form payment detail is not accepted. `payment_webhook_events` stores only event ID/type, SHA-256 digest and processing outcome; raw webhook JSON, PAN, CVV, card expiry and card tokens are never persisted. Webhook idempotency is unique by provider event ID. Provider IDs and checkout/refund idempotency keys are unique where present. Receipt identifiers use random UUID-derived values, not patient identifiers. Financial retention, invoice numbering, tax composition and reconciliation scheduling are TBD. The historical payment status `verified` may exist in databases from earlier demo routes; migrations preserve it pending an approved data-reconciliation policy and do not treat it as a newly verified status. Invoice status is updated server-side to issued, partially_paid, paid, partially_refunded or refunded based on net posted receipts; confirm the policy in OQ-044.
